# DACON 236749: AI Deepvoice Detection Challenge

This repository is a self-contained workspace for the **AI Deepvoice Detection Challenge for Combating Voice-Based Crime**. It contains the public input-format package and the baseline inference implementation. This document is intended to provide all competition context required to onboard a person or an agent without consulting an external page.

## 1. Problem background

Generative AI and speech-synthesis technology have advanced to the point where generated speech can be difficult to distinguish from real speech. Deepvoice technology is increasingly used for voice phishing, voice impersonation, and misinformation. Detection systems must therefore generalize across different generation methods and audio transformations introduced by real communication channels.

Audio generation and manipulation also apply to music and other non-speech signals. The detector must handle audio containing speech alone, music alone, or speech and music together, and must identify both the presence of each component and whether each component was AI-generated.

## 2. Competition objective

Develop an AI model for detecting AI-generated or manipulated speech and music in audio related to emerging voice-phishing crimes.

The task is a five-output probabilistic prediction problem. For every input file, predict a value in `[0, 1]` for each of:

| Column | Meaning |
|---|---|
| `FILE_FAKE_PROB` | Probability that the complete file is fake |
| `VOICE_FAKE_PROB` | Probability that the voice component is AI-generated |
| `MUSIC_FAKE_PROB` | Probability that the music component is AI-generated |
| `VOICE_PRESENT_PROB` | Probability that a voice component is present |
| `MUSIC_PRESENT_PROB` | Probability that a music component is present |

## 3. Evaluation data

- Number of evaluation files: **1,200**.
- Duration per file: **4 seconds to 1 minute**, inclusive of the stated range.
- Standard sample rate: **16 kHz**.
- File formats may include **MP3, WAV, FLAC**, and other common audio extensions.
- Some files contain telephone-channel audio.
- Every file must be processed independently.
- The real evaluation files are private and are not distributed to participants.

The public package contains only three dummy audio files for validating the expected input format. During evaluation, the server replaces `data/test/` with the private evaluation data while preserving the same directory structure.

## 4. Audio categories

### Voice

Audio containing human speech or vocals only.

### Music

Audio containing accompaniment, instruments, or other non-vocal music only.

### Mixed

Audio containing voice and music simultaneously or sequentially.

Vocals are treated as a **voice component**. Therefore, a song containing vocals and instrumental accompaniment is a mixed audio file.

## 5. REAL and FAKE definitions

- A voice or music component generated by AI is **FAKE (1)**.
- A voice or music component originating from a real source and not generated by AI is **REAL (0)**.
- If either the voice component or the music component is fake, the complete file is classified as **FAKE**.
- Post-processing that does not create a new voice or music component—such as quality enhancement, noise reduction, or volume adjustment—does not change a real source into a fake sample.

FAKE is the positive class (`1`) for all EER calculations.

## 6. Leaderboard metric

The final score is a weighted combination of AI-generated audio detection and component-presence performance:

```text
Score = 0.9 × ADS + 0.1 × CPS
```

### 6.1 AI-Generated Audio Detection Score (ADS)

```text
ADS = 0.5 × (1 − File EER)
    + 0.2 × (1 − Voice EER)
    + 0.3 × (1 − Music EER)
```

- **File EER:** file-level fake detection.
- **Voice EER:** voice-component fake detection.
- **Music EER:** music-component fake detection.
- Voice EER is calculated only among samples in which voice is present.
- Music EER is calculated only among samples in which music is present.

The competition defines EER as follows:

```python
fpr, tpr, _ = roc_curve(
    y_true,
    y_score,
    pos_label=1,
    drop_intermediate=False,
)
fnr = 1 - tpr
idx = np.argmin(np.abs(fpr - fnr))
EER = (fpr[idx] + fnr[idx]) / 2
```

### 6.2 Component Presence Score (CPS)

```text
CPS = 0.5 × Voice Presence ROC-AUC
    + 0.5 × Music Presence ROC-AUC
```

### 6.3 Public and private scores

- Public score: calculated on the full test dataset.
- Private score: the competition specification states that the score at the competition closing time is used as the private score.
- The final ranking is based on the total `Score` after the relevant evaluation and verification procedures.

## 7. Competition and selection process

The competition has two evaluation stages:

1. **First-stage evaluation:** The top 15 teams according to the private leaderboard advance to the second stage.
2. **Second-stage evaluation:** Advancing teams submit a model-development report and a training-data construction report. These materials are reviewed together with the first-stage result, and the final top 7 teams receive awards.

The second-stage assessment is performed by a professional judging panel through written review.

The model-performance component of the second-stage evaluation is specified as:

```text
Model performance points =
30 × (team public score / highest public score among second-stage teams)^N
```

`N` is a private adjustment coefficient between 1 and 5.

The public competition information lists a total prize pool of **42,000,000 KRW**.

## 9. Code-submission format

The submission is a `submit.zip` archive. Its top-level structure must match exactly:

```text
submit.zip
├── model/                 # participant-provided model files and weights
├── script.py              # executable inference script
└── requirements.txt       # pip-installable Python dependencies
```

There must not be an additional top-level directory enclosing these files. A structural mismatch can cause an installation error.

The evaluation server automatically adds:

```text
submit.zip
├── model/                 # participant content
├── script.py              # participant content
├── requirements.txt       # participant content
├── data/                  # private evaluation data, read-only
└── output/
    └── submission.csv     # required inference output
```

Requirements for `script.py`:

- Read evaluation inputs from `data/`.
- Write predictions to `output/submission.csv`.
- Use UTF-8 encoding for CSV files.
- Produce one row for every evaluation file.
- Match the five-column prediction schema shown above, together with the required file identifier column from the sample submission.
- Process all supported audio formats without depending on an internet connection.

`data/` is read-only during evaluation. `output/` is created for the inference result, and `submission.csv` must be generated there.

## 14. Package installation and inference policy

Two error classes are distinguished:

1. **Installation error:** problems with the `submit.zip` structure or package installation. These do not count against the daily submission limit.
2. **Submission error:** any error raised while executing `script.py`. These count against the daily submission limit.

The inference code must not download models or other resources after package installation. All runtime resources required by the model must be included in `model/` or be available in the evaluation image.

## 15. Competition rules

- Any methodology is permitted if it has no legal restrictions.
- Participants may use pretrained models, APIs, external data collection, and generated data when legally permitted.
- Every component used must have a clearly documentable source for the second-stage materials.
- Additional training, tuning, or pseudo-labeling using private evaluation data is prohibited.
- Preprocessing, post-processing, and inference-time processing are allowed, provided they do not update the model using private evaluation data.
- Each private-evaluation file must be predicted independently.
- Splitting one file into segments and aggregating its segment predictions is allowed.
- Using information, predictions, or statistics from other files to generate or calibrate a file’s prediction is prohibited.
- The maximum team size is 5 people.
- A participant may not simultaneously belong to an individual entry and one or more teams, nor to multiple teams.
- Individual participation does not require forming a team.
- The maximum number of submissions per day is 3.
- Python is the only allowed programming language.
- Exploiting the code-submission mechanism to exfiltrate evaluation data results in immediate disqualification.
- Fraudulent submissions are prohibited and prior fraudulent-submission history may restrict evaluation eligibility.

## 19. `uv` development environment

This project uses `uv` rather than a manually managed `pip` workflow.

### Create the environment

```bash
cd ~/workspace/deepvoice
uv venv
```

The project is pinned to Python 3.11 through `.python-version` and `pyproject.toml`.

### Install local runtime dependencies

```bash
uv sync --group runtime
```

For a requirements-file workflow, the equivalent shared dependency set can be installed into the uv-managed environment with:

```bash
uv pip install -r requirements.txt
```

The local runtime group contains the Python packages needed by the baseline except PyTorch and TorchAudio. Install a compatible local CPU or CUDA build of those packages separately if they are not already installed. The competition image supplies:

```text
torch==2.7.1+cu128
torchaudio==2.7.1+cu128
```

The competition submission continues to use the required top-level files `script.py`, `model/`, and `requirements.txt`; the `uv` project files are for local development and reproducibility.

### Run the baseline locally

The baseline defaults to CUDA and expects the competition-style directory layout:

```bash
uv run --with torch --with torchaudio python script.py \
  --test-dir data/test \
  --sample-submission data/sample_submission.csv \
  --output output/submission.csv \
  --device cpu
```

For a real local model run, the required pretrained weights must be present under the root `model/` directory. These large files are intentionally not part of Git.

## 20. Onboarding checklist

1. Enter the repository:

   ```bash
   cd ~/workspace/deepvoice
   ```

2. Create the Python 3.11 environment:

   ```bash
   uv venv
   ```

3. Install the local runtime group:

   ```bash
   uv sync --group runtime
   ```

4. Confirm that PyTorch and TorchAudio are available and compatible with the selected CPU/CUDA configuration.
5. Inspect `data/sample_submission.csv` and the three dummy files to validate file discovery and output formatting.
6. Keep all large model weights outside Git while ensuring the selected branch's required checkpoints are present under the root `model/` directory.
7. Run `./package_submission.sh` from the repository root. The helper creates an archive whose top level contains exactly `model/`, `script.py`, and `requirements.txt`.
8. Confirm that inference writes `output/submission.csv` and that all five probabilities are within `[0, 1]`.
